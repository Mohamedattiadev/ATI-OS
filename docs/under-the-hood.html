How it works

The reasoning behind the decisions. Nothing here is needed to use the desktop.

The shape of the thing

The project splits in two, and it matters which half you are on.

HalfPortable?Why
The configs and the ~45 bundled commandsAny LinuxNothing is hardcoded to a distribution, username, monitor, GPU or resolution. Paths come from $HOME, the battery and webcam from /sys and v4l2, screens from live xrandr, DPI from the panel, fonts from fc-match
The installerArch onlypacman, yay, the AUR, dcli, mkinitcpio, systemd-boot

That second row is a deliberate limit. Hand-writing apt and dnf equivalents for 278 packages nobody has ever installed on those systems produces a config that looks portable and breaks on first contact. Worse than saying no.

So the installer fails immediately on a non-Arch system, before touching anything. Every standalone script detects what it needs and exits cleanly with a message rather than half-applying. The desktop half deploys anywhere by hand through stow_script.sh.

Graphics

x86_64 only. The gpu step reads the graphics card's vendor id and installs the matching drivers, then reads the CPU type and installs the matching microcode. A laptop with switchable graphics gets both sets. A virtual machine gets neither, because the generic driver is already correct there.

This matters more than it sounds. The compositor asks for hardware acceleration, so a machine with no driver for its actual card silently falls back to software rendering. The animations, rounded corners and shadows the desktop is built around either crawl or vanish, with nothing in the logs pointing at a package list.

NVIDIA additionally gets one optimisation disabled in a per-machine file, because its proprietary driver is the one stack where that optimisation smears during animations.

ARM is not supported. The step detects a non-x86_64 machine and skips hardware detection rather than installing something wrong. But four required community packages are not all built for ARM, so a full install will not complete.

The USB image

ScriptJob
aur-repo.shBuilds 31 community packages in a clean isolated environment
build-iso.shStages the profile, those packages and the dotfiles, then builds the image
test-iso.shFour-phase test in a virtual machine: bootloader, install, boot, filesystem

The split is deliberate. Rebuilding 31 packages to change a boot-menu label would be absurd, so the first script's output is cached and the second only checks for it.

Everything is written under ~/ati-os-build, never into the git checkout. On the author's machine / has about 6 GB free and /home has 100.

The profile is a fork, kept close

It is a fork of Arch's own standard image recipe, kept deliberately close to the original. Every line that differs has to be reconciled by hand whenever the original changes upstream. The whole difference is branding and the installer script.

An image is a snapshot, not a product

The signing keys baked into it expire in one to two years. After that it cannot install anything, and its kernel stops recognising new hardware. That is Arch being Arch, not a defect.

The build is unattended, so the honest version of "always works" is cheap to regenerate, not never expires. Rebuild every six months.

The prebuilt software

The USB route takes 20 minutes instead of two hours because four packages ship compiled. One of them, a statically-linked package manager kept as an emergency tool, is an hour on its own.

The trust model

Those packages are added to the new system as an unsigned source. That is defensible for one reason: the packages and the tool reading them arrive on the same read-only medium, so a signature would only verify the medium against itself.

The source is removed again at the end of the install. The finished system is never left with a permanent unsigned software source.

The packages are copied into the target rather than referenced on the stick, because the package manager running inside the new system cannot see the live medium's mount point.

Adding a software source without syncing its index breaks every install on the system, not only ones wanting a package from it. That cost two full test runs.

It presented as "Failed to install gum", because gum happens to be the first thing fetched. It was not a gum problem. Every package install on that machine was broken. The installer now syncs, then verifies that the index exists and that packages resolve out of it.

Why they expire

Everything else on an image ages harmlessly because it is refetched at install time. The prebuilt packages are the exception. They were compiled against one build day's libraries and then installed beside whatever the mirrors serve today.

AgeWhat happens
Up to 180 daysUsed
181 to 365 daysUsed, with a warning that a rebuild is safer
Over a yearNot used. Compiled from source instead: correct, and two hours rather than twenty minutes. The disk requirement rises from 30 GB to 60 GB, because build trees are large

Past that point the honest move is to stop using them. That is a bad trade to make silently and a good one to make rather than hand somebody a desktop that breaks in a month.

Why everything checks first

Every entry point runs a preflight that names the value that failed rather than saying "requirements not met". Each check exists because that failure happened and was expensive to diagnose.

CheckThe failure it prevents
UEFI firmwareEvery boot-related step here is written against one bootloader. A second, untested way to boot is the worst kind to ship
Secure BootNot fatal at install time because it is fatal later and far more confusingly. The install completes, the machine reboots, the firmware silently refuses an unsigned bootloader, and the user sees "no bootable device" and blames the installer
The clockA wrong date makes every signature look expired, and the tool reports that as a signature error rather than a clock problem
Disk sizeA finished install is about 20 GB. An earlier version asked for 25, which looked fine and left nothing for the cache, the journal or your files. Running out at step 30 presents as five unrelated steps reporting "No space left on device"
Real disks onlyA plain disk listing includes loopback and RAM devices. On a live medium the compressed filesystem alone adds one, and the first version of that screen showed twenty entries on a machine with one SSD. Asking someone to pick which to erase out of that is how the wrong disk gets chosen
Disks held open by other storage layersPartitioning succeeds and stays invisible to the kernel until reboot, so the install proceeds against a stale view of the disk

Encryption is offered, never imposed

Right for a laptop, wrong to force. The trade is real: a passphrase at every boot, and a forgotten passphrase means the data is gone. There is no recovery, by design.

So the question is asked plainly with the cost stated, rather than defaulted to "secure" on someone's behalf. The 8-character minimum exists because a guessable phrase is worse than no encryption. It feels safe.

The keyboard and language questions are not niceties

The first version wrote no console keymap at all. Every installed machine came up with a US keyboard whatever hardware it had, so somebody on an AZERTY or Arabic keyboard would type their own password wrong at the first login with no way to tell why.

Whatever language is chosen, US English is generated as well. A surprising amount of tooling assumes it exists and misbehaves confusingly without it.

The installer

"It never asks you anything" is a guarantee

install.sh is wizard.sh --yes. Every step runs with its input closed, and the wizard refuses to reach a prompt in that mode.

This used to be untrue twice over. The run stopped dead at the end on a password prompt. And any step whose child process asked a question hung forever behind the spinner, showing nothing but an animation. Both are fixed.

The installer also keeps admin permission alive for the whole run, refreshed in the background, so long builds do not silently drop package installs when the credential cache would expire mid-run.

The step order is load-bearing

The list is generated from the installer's own order array, not maintained by hand. The hand-maintained version had drifted to 36 rows against an installer that ran 48, so eleven steps ran on every machine and were documented nowhere.

The important constraint: the startup splash runs immediately after the rescue boot entry. That is what makes the splash safe to have on by default. The verbose rescue entry always exists before anything touches the primary boot settings.

Every step has a reversal, including the no-ops

The wizard refuses to start if a step is ever added without one. The alternative is discovering that part-way through an uninstall, with earlier steps already reversed.

Several reversals are deliberate no-ops. Reversing them would delete packages, hundred-megabyte downloads, or a 13-times-faster build that an uninstaller has no business touching. So is the Wi-Fi and Bluetooth step: disabling the network to "reverse" an install leaves a machine with no network and no interface to fix it with.

Filters need an equals sign

--only foo with a space is rejected, not ignored. An ignored filter means the full install runs instead, and its eighth step installs every declared package. Unknown flags and unknown step names fail the same way: exit 2, nothing touched.

Two steps are opt-in

The promise is a working desktop, not a working workstation. Docker, a JDK, printing and virtualisation are a second pass you run when you need them. Keeping them out of round one is what keeps the first boot short and predictable.

The Caps-Lock step is opt-in for a different reason. It repurposes Caps Lock outright with no fallback, which is right for one laptop with a dead Alt key and surprising everywhere else.

Why the username is the key

Package sets and settings profiles are keyed off the username, not the hostname, even though the configuration field is called host:.

It reads like a bug and cannot be renamed. That field belongs to dcli's schema, not this project's, and the string is compiled into the dcli binary. Renaming it would stop dcli finding its own configuration.

The behaviour is also the one wanted. These are per-user package sets, and two accounts on one machine legitimately want different ones. It is documented in place so the next reader does not "fix" it.

How the settings files get deployed

stow_script.sh wraps GNU stow, which links a folder of files into your home directory. Editing a file in the project immediately changes the live configuration, with no copy step to forget.

Four things it does that a plain stow . does not:

  1. It derives its own location. The project is routinely checked out elsewhere, and hardcoding ~/.dotfiles made it silently deploy a different checkout than the one it was run from.
  2. It backs up before linking, into ~/DefaultConfig/<timestamp>/. Only regular files are moved at the top level. An existing directory is not a conflict, and moving a real ~/.claude out from under the user would be destructive rather than helpful.
  3. It creates ~/.config first, so stow descends into it instead of folding the whole directory into one link. That would pollute the project with every future application's settings.
  4. It refuses to back up anything the ignore list excludes. Moving a file stow was never going to link only relocates your data for nothing.

What is excluded, and why

The project's own prose is excluded by pattern, not by name. Without those patterns, stow symlinked all seven markdown files into the home directory. Nothing reads them there. Patterns rather than names, because the list was already out of date the first time it was written.

.claude is excluded for a sharper reason. It is a directory stow would fold into the user's existing one rather than skip. That happened once, leaving a link back into the project inside the user's global configuration.

How software is declared

Every package is declared in YAML and reconciled by dcli. Change a file, run dcli sync, and the system converges. A snapshot is taken every sync, so a broken update is a one-command rollback.

Three files are never synced automatically

FileWhy
The three graphics-*.yamlEach is correct on exactly one class of machine. The gpu step reads live hardware ids and installs whichever matches. NVIDIA uses the source-built driver, not the prebuilt one, because the prebuilt module is built against the current kernel only. Booting the rescue entry would come up with no NVIDIA driver at all, which is precisely the fallback you installed for emergencies
splash.yamlThe splash program is inert until it is wired into the boot process, and doing that is a decision about how the machine boots, not a package choice
optional.yamlDocker, JDK, printing, virtualisation. Installed only on request

graphics.yaml holds the vendor-neutral base only. It used to hardcode the Intel driver set with AMD commented out below it, which on an AMD or NVIDIA machine installed Intel drivers and nothing for the actual hardware.

One package is an hour of every install

pacman-static compiles the package manager and every dependency statically from source, much of it single-threaded. It is a genuine safety net. The day it matters is the day nothing else on the machine can install anything.

It is also the single biggest cost in a fresh install, and nothing said so until it was measured. Moving it to the optional list is a one-line change if faster installs are worth more than the net.

The update safety net

  1. A hook that refuses an upgrade when the disk is too full. It fires for any tool, so it cannot be bypassed.
  2. A pre-update hook that blocks on low space, on snapshots stored on the root device itself, or on an inconsistent package database. It refuses, it does not repair, and it cannot be skipped by accident. A safety check you can click past is not a safety check.
  3. A post-update hook that finds packages broken by a library version bump and puts the repair command on your clipboard.

The recovery ladder: downgrade the package, then the fallback kernel at the boot menu, then the rescue entry with every driver loaded, then a repair from an Arch USB stick, then a snapshot restore.

The boot chain

Why there is a rescue entry

The boot-fallback step writes two boot entries for the long-term-support kernel: a normal one and a rescue one with every driver loaded. The kernel package alone ships none, so without this the rescue kernel is installed but unreachable.

Both stay verbose. The step strips the quiet and splash options from them. A rescue entry that inherited the splash would show a logo while hiding the kernel messages saying what broke, which is indistinguishable from the failed boot you are escaping.

The startup splash

Arch boots with the kernel log on screen: a wall of scrolling text ending in a mirror list. Worse than ugly. A boot with no feedback is indistinguishable from a boot that has hung.

The replacement is the username in block art up in the upper third, the Arch mark small and quiet underneath it, and three dots near the bottom edge, all in the current colours.

There is no ring. One was tried, and neither size worked: an arc large enough to read as motion became a second focal point competing with the name, and one small enough to stay subordinate read as a stray dot with nothing legible happening in it.

The three dots do two jobs at once, so a slow boot never looks hung. A wave travels through them continuously — each dot offset in phase from the last, so it reads as travel rather than a blink — and that keeps moving even when no progress is reported, which is most of a fast boot. Separately they fill left to right, in the accent colour, with real progress when there is any.

The accent colour has exactly one job on that screen, the progress dots. So the name is drawn in the foreground colour. A composition where the largest element and the status indicator share a colour has nothing to direct the eye with.

Details that took measuring

  • The logo is read from the distribution's own file rather than copied in, recoloured through its transparency as a stencil, with the trademark glyph removed programmatically. At this size it is a few pixels of grit, and cropping cannot reach it without cutting the logo's feet.
  • The block art comes from a 40-glyph text table, not from a text-art program. That typeface is a contributed one that does not ship with the program, so using it would mean both a new dependency and copying in a font file of uncertain licence.
  • It is rendered solid. The typeface draws the letters with block characters and their shadow with box-drawing characters, and one render pass fills both in the same colour, producing a hollow double outline that reads as a cheap 3D bevel. Only the block characters are kept. A one-pixel kerning adjustment closes the seam the fixed-width spacing leaves down the middle of each letter: invisible in a mock-up, obvious in cream on dark.
  • Everything is a fraction of the screen, not a fixed pixel count. The name is centred on 38% of screen height, the mark is 6% of screen height, and the dots sit at 81%. The splash script recomputes the same arithmetic at boot from the real screen dimensions, and a check command compares the two: if they disagree, the handover from the firmware's bitmap to the splash's first frame is a visible jump.
  • The indicator is anchored to the bottom of the screen, not hung underneath the name. Gluing it to the name is what produced the old top-heavy stack.
  • The whole theme is four small images — the name, the mark, and two 8-pixel dots — under 3 KB together. The colour transition is a cross-fade between two fixed dot images, because the splash program's scripting cannot tint an image and pre-rendering a colour ramp would mean shipping frames for something two sprites do for free. The animation is opacity arithmetic on six sprites, cheap enough to run at 50fps during early boot without the stutter that per-frame image work causes on slow hardware.

One continuous image

The splash used to be bookended by the Arch logo, about 3 seconds before and 4 after, on both sides of five seconds of actual splash.

Neither was the splash program's doing. Arch bakes a bitmap into the kernel image. The bootloader paints it the moment a boot entry is picked, the splash draws over it, and when the splash quits its buffer is released and the bitmap shows through again until the console is cleared.

So the generator also renders a static image of the same composition at the firmware's resolution, and points every kernel preset at it instead. One picture from the boot menu to the login prompt.

That is also why there is no fade-in. The splash takes the framebuffer the instant it starts, so fading up from zero would make the picture already on screen vanish and reappear. Every element starts at its final opacity, and the first frame is rendered to match the bitmap exactly — down to the dots, whose wave is evaluated at tick zero when the still is composited, so the motion picks up mid-stride instead of stepping.

Why a theme change does not update it immediately

The splash runs before the disk is mounted, so the theme lives inside the boot image. Rebuilding that takes about a minute, far too slow for a colour change. So a theme change regenerates the assets and reports that the boot screen is out of date; boot-splash sync does the rebuild when you want it.

The sixteen checks

enable refuses unless check passes, and a failure changes nothing. Among them: the splash program installed, colour placeholders substituted, the theme script's braces balanced, the theme recognised, a verbose rescue entry existing and not splashed, the rescue kernel present on the boot partition.

The subtle one: the static boot frame must be an uncompressed 24-bit BMP3. The bootloader reads nothing else and silently draws blank for anything else, which looks exactly like a broken theme.

Every file it edits is backed up, and disable restores all of them.

The diagnosis that took two attempts. The splash demanded one particular hook in the boot image configuration; current Arch ships a different one, so it refused on every freshly installed machine.

An earlier guess that this was about the kernel image format was wrong. That check had passed all along. It was found by booting a test disk and running boot-splash check inside it: two minutes, against another 90-minute test run.

Concurrency

Theme changes hold a lock. Keyboard-shortcut spam is dropped rather than corrupting caches. Picker clicks are different: a rapid second click kills the one in flight and starts the newer one, because a dropped click there reads as the picker being broken.

Wallpaper-derived palettes

A precompiler walks the wallpaper folder and produces a palette per image, each forced to a quality bar: the strongest contrast standard for background against text, one step down per accent, and a guaranteed hue spread. Six accent slots with fixed jobs:

color1Urgent. Always warm
color2Dominant, the main wallpaper hue. Bar accents pin here
color3Warm fill
color4Cool fill
color5Complement
color6Info

A test harness validates 12 hue buckets end to end.

Why web page content is not force-darkened

A force-dark browser flag used to sit in all three browser configs. It is a per-pixel colour transform applied after render, with no knowledge of the page's design. Fine on a site with no dark theme. Destructive on one that has a good one, because it re-darkens an already-dark palette and blows out gradients and accent text.

The replacement is a preference, not a transform. The desktop advertises a dark colour scheme, the browser reads it, and each site serves its own dark stylesheet.

Fonts fail silently, and that has cost three incidents

The font system never errors on a missing family. It substitutes quietly, and here anything unknown resolves to a CJK face. Every padded column in this project is aligned with spaces, and spaces only align in a fixed-width font. So a missing font presents as "the layout code is broken", with nothing in any log.

Adding a font therefore takes two edits: declare the package, and add the family to the check in validate.sh. That list is hand-maintained and does not derive itself, which is a known weakness. Real family names are rarely what you would guess. One package installs "FiraCode Nerd Font", not "FiraCode Nerd". This project has fallen into that twice.

How it fits any screen

Every pixel value was tuned on a 1366×768 14-inch panel. Copied unchanged to a 15-inch 4K laptop, that is a sliver of a bar with unreadable text. It is the one thing dotfiles cannot keep identical by copying files, because the right answer depends on the glass.

ui-scale computes a factor from the display's real DPI. The window manager multiplies every font size, bar height, icon and margin by it, and a second setting carries the same factor into applications, menus and notifications. It runs at every login, so docking to an external monitor re-scales.

Physical size, not resolution. A 24-inch 1080p monitor sits further away and has larger pixels, so it correctly stays at 1.00 rather than shrinking. The factor never goes below the reference, because that panel is already small.

Verified proportional, never photographed. At factor 2.0 the popups measure the same 3.6 / 2.0 / 1.4 screenfuls as at 1.0, with the text engine measuring real glyph extents at both. That is a mathematical proof. Nobody has looked at it on a 4K screen.

The restart veil

Restarting the window manager normally means watching every window from every workspace flash across the screen for two seconds. That is unfixable from configuration alone. Its own startup maps every window before the hook that would let you intervene ever fires.

So the restart raises a veil, in a separate process, so it survives the restart replacing the window manager itself. It frosts the desktop, shows a card with each window's real icon, and reports genuine progress from the incoming process rather than a timer. It pauses notifications and keeps itself on top by reacting to window-stacking events. Without its one dependency, the reload falls back to a plain restart.

Layout survives

Window proportions save every 3 seconds. The window-to-workspace map and per-workspace focus order save alongside. Both restore shortly after startup.

Windows you moved by hand stay where you put them even though the automatic placement rules re-fire during the restart. The rule is overridden for any window in the restored map.

Why the popups are popups

The sound, monitor, Wi-Fi and Bluetooth pickers replaced four separate programs. Being drawn by the window manager means no window to manage, no workspace to put it on and no floating rule to write. They close when their mode ends. The tray icons stay as icons only.

The cheatsheets scroll rather than page

Paging tied capacity to size. The only way to show more was to be bigger, and they had grown to 1330×750 on a 1366×768 screen, covering the very window you opened them to ask about. With a viewport that moves, size only decides how much you see at once.

Only one sheet is open at a time, which is what makes "the open one" unambiguous for the scroll keys.

Opening a sheet from the menu goes through the window manager's own channel

Not by replaying keystrokes. Replaying the shortcut could not work: entering it auto-shows the first sheet, so the replayed key toggled it back off and it appeared for a single frame.

The mode chip is not decoration

Every mode announces itself in the bar and lists the keys it accepts, in its own colour. One mode used to persist after each action so actions could be chained. But it swallows every other shortcut on the desktop while open, including the ones that restart the desktop, and nothing said you were in it. A mode you cannot tell you are inside is indistinguishable from a broken keyboard.

The documentation menu

Left-clicking the logo used to open a terminal, which four other shortcuts already do. A desktop with this many shortcuts, themes and custom tools has a discovery problem, not a terminal-launching problem. So the most prominent click in the bar now answers "what can this thing do".

Every section is generated from the live system, because a hand-written menu drifts the moment anything is added, and does it silently.

  • The shortcut list parses the config's syntax tree, not a regular expression. Shortcuts nest several mode levels deep, and a regex pass found 44 of them while losing every mode prefix, so mode keys printed as a bare letter instead of the full sequence.
  • Esc goes up, not out. Only Esc at the top level closes. A menu you have to reopen from the bar after every glance is a menu you stop using.
  • One frame, every section, at 614×432, applied centrally so a new section cannot forget it. They used to inherit the launcher's shape loosely and re-shape on every step, which is worse than being the wrong size. A menu whose frame moves under you is one you stop reading.
  • That frame fixes a 52-character budget, measured from what actually rendered rather than calculated. The arithmetic said 56, and 56 visibly clipped.
  • Troubleshooting rows show the symptom, not the heading. "Rofi" tells you nothing. "Yellow wallpaper but rofi selection shows blue/purple" is what you would type when it happens. It was a two-column layout at 147 characters, wider than the screen. Two columns do not survive the cut to 52: at 24 each, both halves are shredded.
  • Documentation is rendered and read-only. You read the document rather than its markup, and cannot damage the project's own docs by accident. It opens in readonly mode, not with the buffer locked, because locking blocks plugins that legitimately write to their own buffers.

Maintenance is the only section that acts

It replaced a section that listed all 38 bundled tools with their header comments and deliberately never ran any of them. Correct, and a reading exercise nobody opened twice, when the tools are all on the command path anyway.

What nothing surfaced was the slow rot: configuration files never merged after an upgrade, orphaned dependencies, services that failed while you watched a splash screen, a download cache growing without bound. So that is what is there, with a live count on every entry.

Two deliberate omissions. Pending updates come from the bar's cache, never a live check, which would sync package databases over the network and turn a menu draw into a multi-second stall, or a hang with no connection. And the orphan entry opens the list, not a bare confirmation. "Remove 21 packages?" with no names is a prompt you either rubber-stamp or cancel, and neither is a decision.

How this gets tested

LayerTimeCatches
validate.shsecondsParses every tracked shell, Python, fish and YAML file. Loads the window manager config for real. Greps for hardcoded home paths, checks every template has a renderer, runs a full installer dry-run
wizard.sh --auditsecondsDeclared packages against installed ones, both directions

The pre-commit hook runs the first two only. A hook that takes three minutes gets bypassed within a week.

validate.sh exists because the window manager falls back to its stock configuration on an error. The failure mode is a desktop that looks like a stranger's, not an error anyone sees.

container-test.sh populates its container from the list of tracked files, not from the directory and not from a clone. That is exactly what a fresh clone receives, so anything excluded from version control is correctly absent, and staged work gets tested before it is committed. Its repeat-run comparison warns but never fails, because regenerated files legitimately differ between runs.

vm-test.sh --unattended scripts a minimal base system, boots it from its own boot partition, runs the installer, then asserts: zero failed steps, validate.sh passing inside the guest, every boot entry's root device matching the guest's real one, and the window manager starting under a headless display. It checks the log for a silent fallback to the built-in config, because asking for its status answers "OK" either way.

What no layer covers. The container has no display server, no service manager and no hardware bus. The virtual machine has no graphics card, so the compositor and the animations are untested there. A passing run must not be read as though it covered them. Nothing anywhere covers AMD, NVIDIA or a high-resolution panel.

An easier install means the untested paths start reaching strangers' machines. That is an argument for fixing them, not for reading a green test run as though it had.

validate.sh degrades every check it cannot run to "skipped". On a machine where the install failed and nothing is present, it skips everything and exits green. Trust the installer's own summary card on a fresh machine.

The VM test clones from GitHub, so it tests what was last pushed, never the working directory. It refuses to start if the branch is ahead of its remote, so nobody draws the wrong conclusion from a green run.

The two lessons that cost the most

1. On a clean install, the step that reports the failure is almost never the step at fault.

One full disk presented as five broken steps, starting 32 steps after the cause. One blocked package transaction presented as two. Reading the per-step error logs is what separated five root causes from twenty-two symptoms.

All five were invisible on the author's machine, because that machine was the single configuration where the code happened to work:

  • Two packages providing the same virtual dependency. On a clean machine the resolver picks the wrong one, it conflicts with the declared one, and the entire transaction aborts. Five failed steps, nothing installed at all, and the desktop would have come up plain.
  • The install needing more than 40 GB of transient disk.
  • The Rust toolchain having no default selected when the first package needing it is built. The step that sets it runs four steps too late.
  • A news-checking tool that refuses every package transaction until the distribution's news is read. It installs itself mid-sync, and a fresh machine always has unread news. Marking it read as the invoking user does nothing, because its hook runs as root and checks root's state.
  • A self-inflicted one: a cache cleanup deleted a build tree another step rebuilt from. It failed 25 steps later with an empty error log, because it failed through a path that never reaches the error stream.

2. Verify a check against a known-good case before trusting it.

Five separate times the check was wrong, not the code. A compositor assertion that reads "not found" even on a working display. "Dead" documentation links that are anchors inside collapsible sections. A "broken heading" that is a comment inside a code block. Desktop probes reporting a working stack as broken because the daemons were already running. And the compositor filed as "untestable" when the hardware was sitting right there.

Every one would have been a regression.

Where the state lives, and why it moved

Per-user runtime state moved out of the shared temporary directory. The danger was not name collisions. The terminal's control socket sat there world-traversable with remote control enabled, which let any other local account drive the terminal. The runtime directory is private to its owner.
