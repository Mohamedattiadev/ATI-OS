The themes

Pick a theme and everything follows — bar, terminal, rofi, notifications, GTK, Qt, browser chrome, nvim, the boot splash, even the folder icons.

Switching

theme-apply gruvbox   # any preset
theme-apply wal       # follow the current wallpaper
theme-toggle          # the rofi picker

Or press Super+P then c. The picker shows friendly names (wal appears as Wallpaper) and marks the current theme with ●.

Rapid picker clicks preempt: an in-flight theme-apply is killed and the newer one starts, rather than the second click being silently dropped.

Light mode

mono-light is the one light preset. It flips the base GTK theme to Breeze + Papirus-Light; every other mode uses Sweet-Dark + Papirus-Dark. That is what makes GTK apps render properly light-on-white rather than dark widgets on a light palette.

The file manager (pcmanfm-qt) is a Qt application, so it ignores the GTK theme entirely and follows the generated qt6ct/qt5ct palette instead — same colours, different path.

Wallpaper mode

theme-apply wal derives the palette from the current wallpaper, using a precompiled cache. wal-precompile walks ~/Pictures/Wallpapers/ and produces a per-image palette at ~/.cache/qtile/palettes/<basename>.json, each one forced to a doomone-quality bar: WCAG AAA background/foreground contrast, WCAG AA per accent, and a guaranteed hue spread.

Drop any image into ~/Pictures/Wallpapers/ and select it — theme-apply wal auto-runs wal-precompile --only <basename> on a cache miss. There is no manual step.

Palette semantics

Six accent slots, hue-concentrated rather than evenly spread:

SlotRole
color1Urgent — always warm
color2Dominant — the main wallpaper hue. Bar accents pin here
color3Warm fill
color4Cool fill
color5Complement
color6Info / cyan

A test harness at .config/qtile/scripts/wal-visual-test.py validates 12 hue buckets end to end.

Wallpaper vs. theme

Changing the wallpaper re-derives the palette only when the active mode is already wal. On a preset you picked a fixed palette on purpose, so a new wallpaper swaps the desktop image and nothing else.

All three wallpaper setters (dm-setbg, the dmscripts dm-setbg, and the qtile WallpaperPopup) check ~/.cache/qtile/theme_mode before invoking theme-apply wal on a background thread, and fail closed if that file is unreadable.

The boot splash

The splash follows your theme too, but it is the one consumer that cannot update instantly: plymouth runs before / is mounted, so the theme is embedded in the initramfs. Rebuilding that is about a minute — far too slow for a colour change.

So theme-apply regenerates the assets and then tells you the boot screen is out of date. You do the rebuild when you want it:

boot-splash status         # what is installed, hooked and set
boot-splash sync           # rebuild the initramfs to match the current theme

The full command set:

boot-splash generate       # render + install the theme (touches nothing about boot)
boot-splash preview        # an animated GIF at your real resolution
boot-splash preview --real # run plymouth for real on a spare VT
boot-splash check          # 16 pre-reboot safety checks
boot-splash enable         # wire into initramfs + kernel cmdline
boot-splash disable        # reverse all of it

preview renders from the real installed assets using the same arithmetic the plymouth script uses, so the timing and layout you see are the ones it will produce. Running plymouthd from a desktop session shows nothing at all, because plymouth draws to the DRM console and X owns the display — that looks like a broken theme when it is fine, so preview does the honest thing instead.

What it draws

The Arch mark inside a progress ring, with your username underneath as ANSI Shadow block art, in the colours of the active theme. The name is generated, never hardcoded: user ati gets ATI, user beko gets BEKO. Override it with BOOT_SPLASH_NAME:

BOOT_SPLASH_NAME="Mohamed Attia" boot-splash generate && boot-splash preview
BOOT_SPLASH_SIZE=32 boot-splash generate   # bigger, if you want it

Two things move, so a slow boot never looks like a hung one: a comet sweeps continuously around the ring — the liveness signal, which keeps moving even when plymouth reports no progress at all, which is most of a fast boot — and the ring fills clockwise with real progress when it is reported.

One continuous image

The splash used to be bookended by Arch's own logo, for ~3s before and ~4s after. Neither was plymouth's doing: Arch's linux.preset ships --splash /usr/share/systemd/bootctl/splash-arch.bmp, which bakes that bitmap into the UKI as a PE .splash section. systemd-boot paints it the moment a boot entry is picked, plymouth draws over it, and when plymouth quits its buffer is released and the bitmap shows through again.

So generate also renders a static BMP of the same composition at the firmware's framebuffer resolution, and enable/sync point every UKI-building preset at it instead. The presets are pacman-owned, so this is an in-place edit with a backup; a linux package upgrade restores Arch's line, and boot-splash status reports it while sync puts it back.

Three safety properties

  • The LTS rescue entries stay verbose. boot-fallback strips quiet and splash from their options. A rescue entry that inherited the splash would show a logo while hiding the kernel messages saying what broke — indistinguishable from the failed boot you are escaping.
  • enable refuses unless check passes. Sixteen checks run first: plymouth installed, colour placeholders substituted, theme script braces balanced, plymouth recognises the theme, the static boot frame is uncompressed 24-bit BMP3 (systemd-boot reads nothing else and silently draws blank for anything else), the UKI presets point at it, a verbose LTS entry exists and is not splashed, the LTS kernel is on the ESP. A failure changes nothing.
  • Every file edited is backed up as *.bak-boot-splash — mkinitcpio.conf, the kernel cmdline, and each UKI preset — and disable restores them all and rebuilds.
./wizard.sh --yes --only=boot-splash       # re-run just this module
./wizard.sh --uninstall --only=boot-splash # remove it, restore every backup

Concurrency

theme-apply holds a flock on ~/.cache/qtile/.theme-apply.lock. Keybind spam is dropped rather than corrupting caches; picker clicks preempt instead of being dropped.

What is deliberately not themed

Web page content. The dark-mode module sets org.gnome.desktop.interface color-scheme=prefer-dark, which xdg-desktop-portal republishes as org.freedesktop.appearance color-scheme = 1. Chromium reads that key and reports prefers-color-scheme: dark, so each site serves its own dark stylesheet. The browser chrome stays palette-driven.

--enable-features=WebContentsForceDark used to sit in all three *-flags.conf. It is a per-pixel colour transform applied after render, with no knowledge of the page's design — fine on a site with no dark theme, destructive on one that has a good one, because it re-darkens an already-dark palette and blows out gradients and accent text. For the occasional site with no dark theme, enable force-dark for that site from the page menu instead of globally.

busctl --user call org.freedesktop.portal.Desktop /org/freedesktop/portal/desktop \
  org.freedesktop.portal.Settings ReadOne ss org.freedesktop.appearance color-scheme

That should answer v u 1.

The shared UI font

The qtile popups use qtile_extras' default sans family, so dunst (Sans 10) and eww ($ui-font: sans-serif) resolve through the same fontconfig alias rather than naming a family. Restyle all three at once by editing ~/.config/fontconfig/fonts.conf; fc-match sans shows the winner.

Font names fail silently. A family fontconfig does not know renders in a substituted face with no error at all — this repo has hit that three times. Run fc-match on any family name before putting it in a config. validate.sh checks a hand-maintained list of 8 families, but it does not derive itself, so a config that starts naming a new family will pass validation while rendering wrong.
