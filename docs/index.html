The Qtile Dotfiles manual

A complete Arch Linux desktop — tiling window manager, 22 themes that retint every application at once, a drop-stash, a package picker and a boot splash with your own name on it. One command installs all of it.

Read this first if you have just installed. There is no display manager and no autologin. When the machine reboots you land on a black text console with a blinking cursor — that is the install working, not failing. Log in with the username and password you chose, then type letsgo (or startx) to start the desktop. See Your first login.

What this is

This is a dotfiles repository that installs an entire desktop on a clean Arch Linux base system: qtile under X11, a themed bar, a set of keyboard-driven popups, about fifty command-line tools, and the package declarations that put all of it there. It is not a distribution and not a desktop environment — it is one person's desktop, written down completely enough that a second machine can reproduce it.

Two halves, and it is worth knowing which one you are standing on:

What it looks like

The two ways to install

  • From the ATI-OS USB → A bootable installation medium with the expensive compiles already done. Answer seven questions; the desktop builds itself on the first boot. Roughly 20 minutes of unattended work instead of two hours.
  • From a git clone → You already have Arch installed. Clone the repo and run one script; 46 modules run end to end with no questions asked. Set aside an hour or two and about 25 GB.

Both routes end at the same desktop. The USB is faster because pacman-static (an hour on its own), espanso, paru and whisper.cpp ship prebuilt rather than being compiled on your machine.

Your first login

The install deliberately leaves you at a text console. The wizard's disable-dm module disables every display manager it can find (lightdm, gdm, sddm, lxdm); nothing starts X for you and nothing logs you in.

  1. Log in at the TTY with the username and password you chose during the install.
  2. Type letsgo and press Enter. If that is not found, type startx.

Why two commands. letsgo is a fish function, not a shell alias, so it exists only when the account's login shell is fish. The wizard's login-shell module runs chsh to fish — but only if fish installed successfully, and it skips itself with a message if fish is not there yet. On a machine where that happened, startx is the one that works.

letsgo does a little more than startx: it refuses if an X server is already running on :0 and tells you which VT to switch to, and it clears a stale /tmp/.X0-lock left by an unclean exit — the leftover that otherwise makes startx fail with "Server is already active for display 0".

To go back to bash: chsh -s /usr/bin/bash $USER. You then lose letsgo and everything else defined in config.fish at the TTY.

Requirements

  1. Arch Linux, clean base install
  2. X11 only — Wayland is not supported
  3. No display manager — TTY plus letsgo/startx
  4. Packages are managed declaratively via dcli

x86_64 only. The GPU module detects Intel, AMD or NVIDIA from the PCI vendor id and installs the matching driver set plus the right CPU microcode. ARM (aarch64) is not supported: the module detects a non-x86_64 architecture and skips PCI and microcode detection rather than installing something wrong, but several AUR packages this repo depends on (picom-ftlabs-git, qtile-extras, brave-bin, google-chrome) are not all built for ARM, so a full install will not complete.

What is not tested

The repository is explicit about this and so is this manual. What is verified, on a clean Arch VM: 46 of 46 modules install, validate.sh passes inside the guest, every boot entry's root= matches the guest's real root device, and qtile starts and loads this config rather than silently falling back to its built-in one. On real hardware, additionally: the boot splash, and picom's glx backend with the window animations on Mesa Intel HD 520.

Not verified, because nobody here has the hardware:

  • AMD and NVIDIA graphics. graphics-amd.yaml is reasoned from pacman -Si, never observed on AMD hardware.
  • A real HiDPI / 4K panel. The scaling is proven proportional mathematically — at scale 2.0 the popups measure the same number of screenfuls as at 1.0 — but nobody has looked at it on a 4K screen.
  • BAT1/ADP1 battery naming, reasoned from /sys semantics rather than seen on a laptop that names them that way.
  • The GPU path in any automated test. The VM and the ISO test both run under a headless X server with no graphics hardware, so a green run says nothing at all about compositing or animations.

validate.sh degrades to skips. Every check it cannot run is reported as "skipped", so on a machine where the install failed and nothing is present it skips everything and exits green. On a fresh machine, trust the wizard's own summary card (46 ok / 0 failed) over validate.sh.
