## HIGH-1 · LSP servers are started twice (duplicate clients)

**Files:** `lua/plugins/prime-lsp.lua`, `lua/plugins/mason.lua`

**Symptom:** duplicate diagnostics, duplicate completion entries, ~2× LSP CPU/RAM.

**Evidence:** opening a Lua file in a git project, `vim.lsp.get_clients()` returned:

```
id=1 name=lua_ls  root=/tmp/luaproj  attached_bufs=1
id=2 name=stylua  root=nil           attached_bufs=1
id=3 name=lua_ls  root=/tmp/luaproj  attached_bufs=1
```

Two `lua_ls` clients on the **same root**, on the **same buffer**.

**Root cause — two independent registration paths:**

1. `prime-lsp.lua` uses the deprecated framework `require("lspconfig")[server].setup({...})`.
   On nvim ≥ 0.11 this emits `vim.deprecate(...)` (see `lspconfig.lua:81`) and is scheduled
   for removal in nvim-lspconfig **v3.0.0**.
2. `mason.lua` sets only `automatic_installation = false`. That is a **different option** from
   `automatic_enable`, which defaults to `true` in mason-lspconfig v2
   (`mason-lspconfig/lua/mason-lspconfig/settings.lua:26`) and calls `vim.lsp.enable()` on
   every mason-installed package.

Confirmed: `vim.lsp._enabled_configs` = `{ bashls, clangd, cssls, html, jdtls, lua_ls, pyright, stylua, ts_ls }`
— identical to `mason-lspconfig.get_installed_servers()`.

**Bonus bug from the same cause:** `stylua` is a **formatter**, not a language server, but it is
being enabled as an LSP client (client id=2 above). It attaches and does nothing useful.

**Also note:** `prime-lsp.lua` calls `lspconfig.lua_ls.setup()` **twice** — once inside the
`for _, server in ipairs(servers)` loop, and again in the "SPECIAL CASE: LUA" block with a
different `root_dir`. Collapse these into one.

### Fix

- [x] In `mason.lua`, add `automatic_enable = false` to the `mason-lspconfig` setup
      (keep `automatic_installation = false`).
- [x] Delete the whole `require("lspconfig")` block from `prime-lsp.lua` — the generic
      `for` loop **and** the duplicated `lua_ls` special case **and** the `tailwindcss` block.
- [x] Move per-server settings into LazyVim's `opts.servers` instead (see HIGH-2 — same edit).
- [x] Remove `stylua` from anything that could be read as a server list; it belongs only in
      `mason-tool-installer`'s `ensure_installed` (where it already is) and in `conform.lua`.

### Verify

```lua
:lua =vim.tbl_map(function(c) return c.name.."#"..c.id end, vim.lsp.get_clients({bufnr=0}))
```

Expect exactly **one** `lua_ls` on a Lua buffer and **no** `stylua` client.

## HIGH-2 · `prime-lsp.lua` throws away LazyVim's entire LSP config

**File:** `lua/plugins/prime-lsp.lua`

**Symptom:** the language extras enabled in `lazyvim.json` are mostly inert; LazyVim's LSP
keymaps, inlay hints, codelens and formatting integration never run.

**Evidence:** resolving the plugin spec at runtime:

```
nvim-lspconfig.config defined at /home/ati/.config/nvim/lua/plugins/prime-lsp.lua:23
```

instead of LazyVim's `lua/lazyvim/plugins/lsp/init.lua:165`. In lazy.nvim, a user-supplied
`config` function **replaces** the parent spec's `config`; it does not extend it.

Meanwhile LazyVim still assembles its server table from the extras — verified 11 entries:

```
*, basedpyright, lua_ls, pyright, ruff, ruff_lsp, stylua, ts_ls, tsgo, tsserver, vtsls
```

…and none of it is ever applied, because the `config` that would apply it was replaced.

**Consequence:** these entries in `lazyvim.json` are currently paying install cost for nothing:
`lang.typescript`, `lang.python`, `lang.json`, `lang.yaml`, `lang.tailwind`, `lang.java`,
`lsp.none-ls`.

### Fix

- [x] Convert `prime-lsp.lua` from `config = function()` to `opts = { servers = { ... } }`
      so LazyVim's config still runs. Sketch:

```lua
return {
  "neovim/nvim-lspconfig",
  dependencies = { "j-hui/fidget.nvim" },
  opts = {
    servers = {
      lua_ls = {
        settings = {
          Lua = {
            diagnostics = { globals = { "vim" } },
            format = { enable = true, defaultConfig = { indent_style = "space", indent_size = "2" } },
          },
        },
      },
      -- html / cssls / bashls / pyright / ts_ls: LazyVim's extras already
      -- configure these. Only add a key here if you need to override.
    },
  },
}
```

- [x] Keep the custom `hover_in_split` + `<leader>gd` telescope mapping, but move them into a
      **separate small spec file** with an `LspAttach` autocmd, so they no longer require
      hijacking `nvim-lspconfig`'s `config`.
- [x] Drop `require("conform").setup({ formatters_by_ft = {} })` from this file — `conform.lua`
      already configures conform, and this call only forces conform to load eagerly, defeating
      its `lazy = true`. (Harmless to the format table itself: conform's `setup` merges with
      `tbl_extend("force", ...)`, so an empty table erases nothing — but the eager load is real.)
- [x] Either drop `require("fidget").setup({})` from here too and give fidget its own spec, or
      keep it — but not inside a replaced `nvim-lspconfig` config.
- [x] Decide on `lsp.none-ls`: it is enabled in `lazyvim.json` but `none-ls.nvim` is disabled in
      `disabled.lua`. Pick one — currently it is contradictory.

**Deprecated API used in this file (fix while you are in here):**

- [x] `vim.lsp.util.make_position_params()` with no args → warns
      *"position_encoding param is required … Defaulting to position encoding of the first client."*
      Pass the client's `offset_encoding`.
- [x] `vim.lsp.util.trim_empty_lines()` still exists on 0.12 but is deprecated — trim inline.
- [x] `source = "always"` in `vim.diagnostic.config({ float = ... })` is the old spelling;
      current API expects `source = true`.


## MED-3 · Most of `Prime_treesitter.lua` is silently ignored

**File:** `lua/plugins/Prime_treesitter.lua`

nvim-treesitter is pinned to the **main** branch (the rewrite). LazyVim's treesitter spec
(`lua/lazyvim/plugins/treesitter.lua:111-116`) only honours:

```lua
---@alias lazyvim.TSFeat { enable?: boolean, disable?: string[] }
```

i.e. `disable` must be a **list of language names**. A function is ignored.

**Evidence:**

- `disable = function(lang, buf) if lang == "html" then return true end ... end` → HTML
  treesitter highlighting is still **active** on an `.html` buffer
  (`vim.treesitter.highlighter.active[buf] ~= nil` → `true`). Your HTML rule and your
  100 KB large-file guard are **both** doing nothing.
- `ignore_install = { "markdown_inline" }` → `markdown_inline` **is installed**
  (`require("nvim-treesitter").get_installed()` contains it). `ignore_install` is not part
  of the main-branch API, and LazyVim's own `ensure_installed` list includes markdown_inline
  anyway via `opts_extend`.
- `additional_vim_regex_highlighting = { "markdown" }` → not part of the main-branch API either.

### Fix

- [x] Replace the `disable` function with the supported list form:

```lua
highlight = { enable = true, disable = { "html" } },
```

- [x] Delete `ignore_install` and `additional_vim_regex_highlighting` (dead options).
- [x] If you still want the large-file guard, use LazyVim's `bigfile` support / a `FileType`
      autocmd that calls `vim.treesitter.stop(buf)`, not a treesitter opt.
- [x] Re-test whether you still want HTML highlighting off at all — it has effectively been
      **on** this whole time, so the setting may simply be stale intent.

### Verify

Open an `.html` file → `:lua =vim.treesitter.highlighter.active[0] ~= nil` should be `false`.

**File:** `lua/config/options.lua:42-43`

- [x] Remove `opt.lazyredraw = true`. Neovim discourages it; it suppresses redraws during async
      work. Given how much bookkeeping `lua/plugins/image.lua` does to clear stale kitty images,
      this is the prime suspect for ghost/stale image frames. LazyVim deliberately does not set it.
- [x] Remove `opt.ttyfast = true`. Checked the 0.12 docs while applying this: `'ttyfast'` is

      setting it from `options.lua` could never have had any effect either way. It is only
      controllable via the `$NVIM_NOTTYFAST` environment variable.

## MED-12 · blink.cmp source list was doubled (found while verifying completion)

**File:** `lua/plugins/blink.lua`

Found only when the completion path was tested end-to-end, after the main fix pass.

LazyVim declares `sources.default` in its `opts_extend` list
(`extras/coding/blink.lua:19-22`), which means a user value is **appended** to LazyVim's,
not substituted for it. `blink.lua` re-declared the same four sources, so the effective list
was eight entries:

```
{ "lsp", "path", "snippets", "buffer", "lsp", "path", "buffer", "snippets" }
```

Every provider was registered twice.

- [x] Removed `sources.default` from `blink.lua` (LazyVim's list is already exactly the four
      wanted, and it additionally wires the `lazydev` source for lua buffers).
      Verified after: `{ "lsp", "path", "snippets", "buffer" }`.

**Functionally verified after the change**, by querying the server directly rather than
trusting the UI: typing `vim.ap` in a Lua buffer returns 5 real LSP completion items
(`api`, `ui_attach`, ...), hover returns content, 0 spurious diagnostics, conform resolves
`stylua` for lua, supermaven reports `is_running = true`, lazydev loaded.

## FEATURE · unsaved-file markers in mini.files (requested 2026-07-29)

**File:** `lua/plugins/miniFiles.lua`

Marks files with unwritten changes in the explorer, plus the directories leading to them so an
unsaved file buried in a subfolder is still findable:

```
somefile.lua    ● unsaved      <- unsaved changes  (MiniFilesUnsaved, orange)
src/            ●              <- something unsaved in here (MiniFilesUnsavedDir, purple)
```

Implementation notes:

- Drawn as **extmarks** on the `MiniFilesBufferUpdate` event, not via `content.prefix`:
  `prefix` returns a *single* highlight group for the whole prefix, so putting the marker
  there would force the file icon to take the marker's colour too.
- Registered from `init`, **not** `config` — a `config` here would replace LazyVim's own
  mini.files config, which is exactly the trap HIGH-2 was about.
- Highlights are re-applied on `ColorScheme`, because `themes.lua` runs `hi clear` when it
  switches theme and would otherwise wipe them. Both groups use `default = true`, so a
  colorscheme that defines them wins.
- Paths are compared as normalized absolute paths. The old commented-out attempt used
  `vim.fn.bufnr(path)`, which does *pattern* matching and can match an unrelated buffer.
- `MiniFiles.get_fs_entry` errors on non-directory buffers (the file preview pane), so it is
  wrapped in `pcall`.

Verified live: unsaved file in a subfolder → `dirty.lua -> "● unsaved"` and its parent
`src -> "●"`; the clean sibling file got no marker; after `:write` the markers dropped to 0.

- [x] Implemented and verified.
